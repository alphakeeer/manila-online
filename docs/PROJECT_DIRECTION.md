# Manila 在线多人游戏：产品与架构方向

## 1. 最终产品目标

本项目的目标是实现一个可部署到公网服务器的网页版《Manila》，供一个小型、互相信任的朋友群体进行实时多人游戏。

产品应满足以下核心约束：

- 访问站点和游戏 API 前，用户必须提交一个服务端认可的 **8 位 Token**。
- Token 只承担私人站点的访问控制，不承担完整账号、资料、密码找回或社交关系功能。
- 玩家可以创建房间、加入房间、准备并完成一整局游戏。
- **服务器保存并裁决权威游戏状态；客户端只展示服务器下发的状态，并提交操作意图。**
- 浏览器刷新、短暂断网或 WebSocket 重连后，玩家可以恢复到自己的房间和座位。
- 服务重启后，未结束的房间可以从持久化数据恢复。
- 首个正式版本优先保证少量朋友稳定游玩，而不是支持大规模公开运营。

## 2. 产品原则

### 2.1 服务端权威

规则引擎只在服务端执行权威状态迁移。客户端不能直接写入游戏状态，也不能自行决定骰子结果、资金、股份、可执行动作或结算结果。

客户端提交的内容应是命令，例如：

```json
{
  "commandId": "01J...",
  "roomId": "room_123",
  "expectedRevision": 42,
  "action": {
    "type": "bid",
    "amount": 7,
    "mortgageShareIds": []
  }
}
```

服务端负责：

1. 从会话确定访问者和玩家座位，不能信任客户端传入的 `playerId`。
2. 校验 Token 会话、房间成员关系、当前回合和 `expectedRevision`。
3. 调用共享规则引擎执行 `transition`。
4. 持久化新状态和事件，再增加房间 revision。
5. 向房间成员广播经过隐私过滤的快照或增量事件。

### 2.2 Token 是访问控制，不是账号系统

- Token 必须恰好为 8 位；首版建议限定为不易混淆的大小写无关字母数字字符。
- 有效 Token 由服务器配置或管理脚本生成，并以哈希形式保存；日志、URL、埋点和错误信息中不得记录明文 Token。
- Token 通过 HTTPS POST 提交一次。验证成功后，服务器签发短期或可续期的 `HttpOnly`、`Secure`、`SameSite` Cookie 会话。
- Token 不应保存在 URL 查询参数或浏览器 localStorage 中。
- Token 证明“允许访问这个私人站点”，玩家昵称、房间座位和断线恢复身份由服务端会话记录管理。
- 登录接口需要速率限制、统一失败提示和审计日志，避免暴力枚举 8 位 Token。

### 2.3 私人信息隔离

完整 `GameState` 只能存在于服务端。服务端必须针对每个接收者生成视图：

- 公共信息：版图、舢板、行情、公开同伙、航程和当前行动玩家。
- 当前玩家私有信息：自己的资金、股份、抵押状态和可执行决策。
- 其他玩家私有信息不得通过 WebSocket、REST 响应或前端源码中的预加载状态泄漏。

不能只依赖 CSS 隐藏或客户端删除字段；隐私过滤必须发生在服务端序列化边界。

## 3. MVP 范围

MVP 应包含：

- 8 位 Token 验证和 Cookie 会话。
- 创建房间、使用房间码加入、离开未开始房间。
- 3–5 名玩家的大厅、昵称、座位、准备状态和房主开始游戏。
- 一局完整的标准 Manila 规则，以及项目现有的加强海盗选项。
- WebSocket 实时同步；REST 用于登录、初始加载和房间管理。
- 服务端权威骰子、规则校验、行动顺序和结算。
- 每个房间严格串行处理命令，使用单调递增 revision 防止重复提交和旧状态覆盖。
- `commandId` 幂等处理，客户端重试不会重复扣款或重复行动。
- 断线重连、刷新恢复、同一会话重新取得原座位。
- 房间与游戏状态持久化；进程重启后可以恢复进行中的游戏。
- 基础管理能力：生成/撤销 Token、查看活跃房间、关闭异常房间。
- 桌面和移动浏览器可用，提供明确的连接状态、等待状态和错误反馈。

## 4. 非目标

以下内容不属于首个 MVP：

- 公开注册、邮箱/手机号登录、密码找回、OAuth 或复杂权限体系。
- 排位、匹配、排行榜、好友、聊天、观战和公开房间大厅。
- AI 玩家、单人战役和教学关卡。
- 原生移动 App。
- 大规模多区域部署、微服务拆分或 Kubernetes。
- 区块链、可交易资产或真钱功能。
- 完整反作弊系统。服务端权威和私有数据隔离仍然是必须的基础安全要求。
- 游戏内语音、视频或第三方社交集成。

## 5. 推荐技术架构

### 5.1 仓库边界

建议演进为 npm workspaces 单仓库：

```text
apps/
  web/                  React + Vite 客户端
  server/               Node.js API、WebSocket、房间运行时
packages/
  game/                 纯 TypeScript 规则引擎
  protocol/             命令、事件、公开/私有视图及运行时 schema
  config/               共享 TypeScript、测试和 lint 配置（可选）
docs/
  PROJECT_DIRECTION.md  本文档
manila_assets/          原始素材；构建前应生成压缩后的 Web 资源
tools/
  annotator/            开发期坐标标注工具
```

迁移时应先将现有 `src/game/` 原样提取为 `packages/game/`，确保其仍不依赖 React、HTTP、数据库、系统时间或全局随机数。不要在规则层加入 WebSocket 或数据库代码。

### 5.2 客户端职责

推荐继续使用 React、TypeScript 和 Vite。客户端负责：

- Token 输入页及当前会话状态。
- 房间大厅、准备和断线提示。
- 渲染服务器提供的 `PlayerGameView`。
- 根据服务器下发的 `DecisionView` 展示可执行选项。
- 提交命令并显示 pending/accepted/rejected 状态。
- 保存非敏感客户端设置，例如音量、动画偏好和最近使用昵称。
- WebSocket 断线后指数退避重连；重连成功后请求最新快照，而不是在本地继续推进游戏。

客户端不得：

- 调用规则引擎生成权威下一状态。
- 自行掷骰、结算或推断不应公开的股份信息。
- 把 localStorage 中的状态当作可恢复的权威游戏存档。

### 5.3 服务端职责

首版推荐一个模块化单体 Node.js 服务，避免过早拆分微服务：

- HTTP：Fastify。
- 实时通信：原生 WebSocket 或 `@fastify/websocket`。
- 运行时校验：Zod。
- 数据库：PostgreSQL；本地开发可使用容器化 PostgreSQL。
- 数据访问：Drizzle ORM 或直接使用类型化 SQL。
- 测试：Vitest；协议与房间集成测试启动真实服务实例。

服务端模块建议分为：

- `auth`：Token 校验、会话签发、撤销和限流。
- `rooms`：房间生命周期、成员、座位、准备和房主行为。
- `games`：加载状态、串行命令队列、调用规则引擎、生成接收者视图。
- `realtime`：连接注册、心跳、重连、revision 同步和广播。
- `persistence`：事务、快照、事件记录和恢复。
- `admin`：仅命令行或受保护接口使用的 Token 与房间管理。

### 5.4 房间与同步模型

每个房间至少包含：

- `roomId`、短房间码、状态（lobby/playing/finished/closed）。
- 房主、成员、玩家座位、昵称和连接状态。
- 规则配置、权威 `GameState`、当前 revision。
- 最近处理过的 `commandId`。
- 创建、更新、最后活动和过期时间。

同一房间的写命令必须串行处理。单进程 MVP 可以使用每房间 Promise 队列；数据库写入使用事务和 revision 条件更新。未来如果部署多个服务实例，应改用数据库 advisory lock、Redis 锁或将房间固定路由到单一实例。

WebSocket 消息最少应包括：

- `room.snapshot`：接收者专属完整视图和 revision。
- `room.presence`：成员、准备和在线状态。
- `game.command.accepted` / `game.command.rejected`。
- `game.updated`：新 revision、公开事件和接收者专属新视图。
- `session.expired`：要求重新提交 Token。

客户端发现 revision 跳跃、重连或服务端报告冲突时，应请求完整快照，不应自行合并权威游戏状态。

### 5.5 持久化策略

MVP 推荐“当前快照 + 追加事件”组合：

- `access_tokens`：Token 哈希、状态、创建和撤销时间。
- `sessions`：会话摘要、关联 Token、过期和最后活动时间。
- `rooms` / `room_members`：房间和座位信息。
- `games`：当前序列化状态、规则版本和 revision。
- `game_commands`：commandId、操作者、请求、结果和 revision，用于幂等和审计。
- `game_events`：规则事件和发生顺序，用于结算展示与问题追踪。

每个已接受命令应在同一数据库事务中写入新快照、命令结果和事件。广播只能发生在事务成功提交之后。

`GameState.version` 和协议版本必须保留。上线后修改规则状态结构时需要显式迁移，不能假设旧房间会自动兼容。

### 5.6 部署边界

首版适合单台公网服务器：

- 反向代理终止 TLS，并代理 HTTP 与 WebSocket。
- Web 静态资源和 Node.js 服务可以同域部署，减少 Cookie、CORS 和 WebSocket 配置复杂度。
- PostgreSQL 使用持久卷和定期备份。
- 服务器只从环境变量或秘密管理中读取 Token 管理密钥、Cookie 签名密钥和数据库连接串。
- 提供 `/health/live` 和 `/health/ready`，并记录结构化服务日志，但日志不得包含明文 Token 或私人股份。

## 6. 当前已有能力

当前仓库已经具备：

- 与 React、DOM 和网络无关的 TypeScript 规则引擎。
- `createGame`、`getDecision`、`transition`、`validateState` 和 `getStandings`。
- 可重现 RNG、3–5 人初始化、标准/加强海盗规则。
- 港务长竞拍、购股、货物与航线安排、同伙放置、三轮移动、领航员、海盗、保险、行情和终局结算。
- 规则单元测试、状态不变量测试和随机完整游戏模拟。
- 一套客户端原型，可用真实引擎进行本地热座操作。
- 版图和货物牌语义坐标数据、开发期标注工具。

当前尚未具备：

- 服务端、数据库、Token 验证和会话。
- 房间模型、WebSocket 协议和玩家重连。
- 服务端隐私视图投影。
- 权威命令队列、revision、幂等和持久化。
- 公网部署配置和端到端多人测试。

现有客户端原型的价值是验证版图呈现和操作交互，不应继续承担权威状态职责。接入服务端时，应逐步把本地 `createGame`/`transition` 调用替换为协议客户端，而不是在浏览器和服务器各维护一份可独立推进的游戏。

## 7. 后续开发阶段与优先级

### P0：共享边界与规则可信度

1. 建立 workspace 结构，提取 `packages/game` 和 `packages/protocol`。
2. 为所有命令、事件、游戏视图和错误建立判别联合与 Zod schema。
3. 明确服务端公开视图和玩家私有视图，增加“不会泄漏他人股份/现金”的测试。
4. 修复现有客户端跨玩家残留表单状态，并补齐规则引擎关键边界测试。

### P1：可联机的纵向切片

1. 实现 Token 验证、Cookie 会话和限流。
2. 实现房间创建/加入/准备/开始。
3. 实现一个房间的服务端权威命令队列、revision 和幂等。
4. 用 WebSocket 下发接收者专属快照，并完成刷新与短暂断线恢复。
5. 让客户端通过服务端完成从创建房间到首个竞拍动作的纵向闭环。

### P2：完整游戏与持久化

1. 将全部 Decision/Action 接入网络协议。
2. 实现 PostgreSQL 快照、命令和事件事务。
3. 完成服务重启恢复、房间过期和异常关闭策略。
4. 接入真实结算事件、行动历史和连接状态 UI。
5. 增加两至五个浏览器上下文的端到端整局测试。

### P3：部署与运营保障

1. Docker 化 Web、服务端和数据库迁移。
2. 配置 TLS、反向代理、WebSocket、备份和健康检查。
3. 增加 CI、lint、测试覆盖率、构建和迁移检查。
4. 优化图片体积和首屏资源加载。
5. 提供生成/撤销 Token 和检查活跃房间的最小管理命令。

## 8. 架构决策摘要

- 规则引擎继续保持纯函数式、无网络依赖。
- 服务端是唯一权威状态持有者和规则裁判。
- 客户端只持有接收者专属视图，并提交命令。
- Token 是简单的私人访问门禁，不升级为复杂账号体系。
- 首版使用模块化单体和单一 PostgreSQL，优先可靠性和可运维性。
- 房间写操作串行化，并通过 revision 与 commandId 解决并发和重试。
- 持久化成功后才广播，断线后以服务端快照恢复。
